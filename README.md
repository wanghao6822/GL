# Remote-IO — 直流屏硅链调压器 Modbus 远程 IO 板

基于 STM32F103C8T6 + FreeRTOS + Modbus RTU/TCP 的智能远程 IO 设备，集成**直流屏硅链自动调压控制**功能。

---

## 硬件规格

| 类别 | 参数 |
|------|------|
| **MCU** | STM32F103C8T6 (Cortex-M3, 64KB Flash, 20KB RAM) |
| **系统时钟** | 64MHz (内部 HSI) / 可改 72MHz (外部 HSE 8MHz×9) |
| **供电** | DC 9~24V |
| **数字输入** | 8 路 (X0~X7)，DC 24V，兼容 NPN/PNP，内部上拉，带可配置消抖滤波 |
| **数字输出** | 6 路 (Y0~Y5)，开漏模式，LOW=导通 |
| **模拟输入** | 4 路 (AI0~AI3)，16 位 ADC (ADS1115)，±4.096V 量程 |
| **RS485** | 1 路，Modbus RTU 协议 |
| **以太网** | 1 路，Modbus TCP 协议 |
| **调试串口** | 1 路 TTL (PA9/PA10)，可打印系统运行信息 |

## 核心功能

### 基础远程 IO
- 8 路数字输入采集，带软件消抖滤波（默认 5ms，1~100ms 可配置）
- 6 路数字输出控制，Modbus 远程读写
- 4 路模拟量采集（ADS1115，16 位精度）
- Modbus RTU (RS485) + Modbus TCP (以太网) 双协议并行，**共享寄存器区**
- 独立硬件看门狗（IWatchdog），超时 400ms
- 拨码开关配置站号 (1~7) 和波特率 (9600/19200/38400/115200)
- MAC / IP 地址可配置，掉电保存（EEPROM）

### 直流屏硅链调压器 🆕
- **2 路电压采集**：合母电压 (HM) + 控母电压 (KM)，经降压模块 (分压比 91:1，R上=900kΩ/R下=10kΩ) 后由 ADS1115 采集
- **3 继电器 8 档硅链控制**：Y2/Y3/Y4 编码控制，实现 0~35V 降压调节
- **自动调压模式**：实时检测 KM 电压，自动升/降档维持等于目标值，带死区滞回
- **手动控制模式**：上位机通过 Modbus 直接控制继电器
- **三重报警**：KM 越上限 / KM 越下限 / HM-KM 压差异常，各带 5 秒消抖
- **报警输出**：Y0 硬件导通报警（LOW=报警），寄存器 23 同步上报
- **档位掉电记忆**：当前档位和控制模式保存到 EEPROM
- **可校准降压系数**：HM/KM 各自独立校准 (×100，如 91.00→9100，对应分压比 R上=900kΩ/R下=10kΩ)
- **兼容 110V/220V 系统**：目标电压、每档压降、最大压降等参数均可配置

### 任务优先级设计原理

> 💡 **嵌入式面试高频考点：为什么这样分配优先级？**

```
优先级: 6(Watchdog) > 5(X_filter) > 4(Modbus×2) > 3(IIC + Main)
         ↑              ↑              ↑               ↑
      硬实时安全      软实时采集      通信协议栈      业务逻辑
```

**设计原则：**

| 原则 | 说明 | 对应设计 |
|------|------|----------|
| **安全优先** | 看门狗任务必须拥有最高优先级，确保即使系统负载极高也能按时喂狗 | WatchdogTask @ prio 6 |
| **采集优先于通信** | 输入滤波 1ms 定时采集，若被通信任务阻塞将导致滤波计数不准、漏检脉冲 | X_filter @ prio 5 |
| **通信优先于处理** | Modbus 协议要求从站 100ms 内响应，否则主机超时；TCP 超时更严苛 | ModbusRTU/TCP @ prio 4 |
| **业务逻辑最低** | 硅链调压 1s 周期 + 参数保存耗时操作，可被抢断不影响通信实时性 | IIC + Main @ prio 3 |

**堆栈尺寸估算方法（以 MainTask 256 words = 1024 bytes 为例）：**

```
栈使用 = 函数调用深度 × 局部变量 + 中断嵌套保存上下文 + 安全余量
       ≈ 200 bytes (调用链) + 64 bytes (中断帧) + 200 bytes (余量)
       ≈ 464 bytes → 取 1024 bytes 留有2倍冗余
```

各任务堆栈通过 `uxTaskGetStackHighWaterMark()` 实测验证，当前配置下各任务剩余空间均 > 50 words。

## 硅链调压器工作原理

### 自动调压逻辑 (每 1 秒执行)

```
1. 读取 KM 实际电压 (寄存器 21) 和 HM 实际电压 (寄存器 20)
2. 计算偏差: deviation = TargetVoltage - KM
3. 若 deviation > DeadBandUpper → KM 偏低，升档 (减小降压)
     升档数 = deviation / StepVoltage
4. 若 -deviation > DeadBandLower → KM 偏高，降档 (增大降压)
     降档数 = -deviation / StepVoltage
5. 档位限制: 0~7
6. 写继电器: SetGearOutput(gear) → Y2/Y3/Y4
7. 更新寄存器 22 (当前档位)
```

### 报警检测 (5 秒消抖)

| 报警类型 | 触发条件 | 表达式 |
|----------|----------|--------|
| 越上限 | KM > 目标电压 + 死区上限 | `KM > Target + DeadBandUpper` |
| 越下限 | KM < 目标电压 − 死区下限 | `KM < Target − DeadBandLower` |
| 压差异常 | HM − KM > 最大压降 | `HM − KM > MaxDropVoltage` |

任一报警触发 → Y0 导通 (LOW) + 寄存器 23 = 1

### 调压算法深度解析

> 💡 **嵌入式面试高频考点：请解释硅链调压的控制算法**

#### 核心思想：滞回比较器 + 死区控制

硅链调压本质上是一个**离散型滞回控制器**（Hysteresis Controller with Discrete Output）。与 PID 等连续控制器不同，硅链只有 8 个离散档位（0~7），因此采用**基于偏差的步进式调节**。

#### 数学模型

设目标电压为 \\( V_{target} \\)，当前 KM 电压为 \\( V_{km} \\)，每档压降为 \\( V_{step} \\)：

$$deviation = V_{target} - V_{km}$$

**升档条件（KM 偏低，需减小降压）：**
$$deviation > DeadBandUpper$$

**降档条件（KM 偏高，需增大降压）：**
$$-deviation > DeadBandLower$$

**死区（不调节区）：**
$$-DeadBandLower \leq deviation \leq DeadBandUpper$$

#### 死区设计的工程意义

```
KM 电压
  ↑
  │  越上限报警区  ──── Target + DeadBandUpper + StepVoltage
  │
  │  死区(不调节)  ──── Target + DeadBandUpper
  │                     Target - DeadBandLower
  │
  │  降档区        ──── Target - DeadBandLower - StepVoltage
  │
  ↓  越下限报警区
```

如果不加死区，KM 电压在目标值附近微小波动时，系统会反复升降档位，导致继电器频繁切换（**继电器振荡 / Relay Chattering**），严重缩短硬件寿命。死区创造了"无反应区"，使系统在目标值附近保持稳定。

#### 步进计算方法

```cpp
// 升档：KM偏低，减小降压（档位+1~+N）
uint8_t steps = deviation / StepVoltage;  // 计算需要升几档
if (steps == 0) steps = 1;                // 至少升1档，避免死循环
newGear = CurrentGear + steps;            // 限幅 0~7

// 降档：KM偏高，增大降压（档位-1~-N）
steps = (-deviation) / StepVoltage;
if (steps == 0) steps = 1;               // 至少降1档
newGear = CurrentGear - steps;           // 限幅 0~7
```

**为什么用 `deviation / StepVoltage` 而不是每次只调 1 档？**

当系统刚上电或负载突变时，KM 电压可能偏离目标很远（例如偏差 15V，每档 5V = 需要 3 档）。一次性调到目标档位比逐档调节快 3 倍，大幅缩短恢复时间。这是**比例式步进**（Proportional Step）而非固定步进。

#### ADC 原始值 → 实际电压换算（整数优化）

> 💡 **考点：Cortex-M3 无硬件 FPU，为什么不能用 float？**

**原版（浮点运算）：**
```cpp
float voltage = (float)adcValue * 4.096f / 32767.0f * (float)calibration / 100.0f;
return (uint16_t)(voltage * 100.0f);
```

**优化版（纯整数运算）：**
```cpp
// stored = adcValue × 4096 × calibration / 32767000
return (uint16_t)(((uint64_t)adcValue * 4096 * calibration) / 32767000);
```

| 对比维度 | 浮点版本 | 整数版本 |
|----------|----------|----------|
| CPU 开销 | ~200+ 周期（软浮点库） | ~50 周期（硬件整数除法） |
| Flash 占用 | 链接软浮点库 +2KB | 无额外库依赖 |
| 精度损失 | IEEE 754 舍入误差 | 单次整数截断 < 0.01V |
| 溢出风险 | float 范围大 | uint64_t 中间值最大 32767×4096×9999 ≈ 1.3×10¹² < 2⁶⁴ |

这是典型的**嵌入式定点运算优化**——用整数放大 100 倍存储（单位 0.01V），避免小数点，既保证精度又避免软浮点性能损失。

### 1. 整体架构设计思想

#### 为什么选 FreeRTOS 而不是裸机（Bare Metal）？

| 维度 | 裸机（Super Loop） | FreeRTOS（本方案） |
|------|-------------------|---------------------|
| 多任务并发 | 需手动状态机拆分，复杂逻辑下难以维护 | 6 个任务独立运行，各自专注单一职责 |
| 实时性保证 | 依赖开发者逐一检查每个循环路径的执行时间 | 抢占式调度，高优先级任务微秒级响应 |
| 可扩展性 | 新增功能需重新评估整个循环时序 | 新增任务只需分配优先级和堆栈 |
| 调试难度 | 时序耦合导致 Bug 难以复现 | 任务隔离，问题定位更清晰 |

**裸机改写成本分析：** 若将本项目改为裸机实现，需要：
- 1ms 定时器中断服务消抖滤波
- 主循环轮询 Modbus 帧 + 硅链调压 + IO 刷新
- 任何一处阻塞（如 EEPROM 写入）会导致 Modbus 超时丢包
- 估计需要 3 倍代码量才能达到同等可靠性

#### 为什么用 Arduino 框架而不是 STM32 HAL/LL 库？

| 维度 | STM32 HAL | Arduino (本方案) |
|------|-----------|-------------------|
| 开发效率 | 寄存器配置繁琐，外设初始化代码量大 | `digitalWrite()` / `Wire.begin()` 一行搞定 |
| 库生态 | 需自行移植/适配 | PlatformIO 上万库直接引用 |
| 学习曲线 | 陡峭（需读 Reference Manual） | 平缓，初学者友好 |
| RAM/Flash 消耗 | 较小（按需编译） | 略大（框架基础开销 ~2KB） |

**选择理由：** 项目定位为快速交付 + 后续维护简单。STM32F103C8 的 64KB Flash / 20KB RAM 对 Arduino 框架完全够用（当前编译后 Flash 占用约 48KB）。

### 2. Modbus 双协议共享寄存器设计

> 💡 **面试亮点：这不是简单的"两个协议各开一个服务"，而是真正共享底层数据。**

#### 架构图

```
┌──────────────────────────────────────────┐
│              寄存器共享区                  │
│       uint16_t _regs[31] (地址 0~30)       │
├──────────────────────────────────────────┤
│         ▲                     ▲          │
│         │                     │          │
│   ModbusRTUTask         ModbusTCPTask     │
│   (prio 4, RS485)       (prio 4, TCP)     │
│   从 _regs[] 读取        从 _regs[] 读取    │
│   写入 _regs[]           写入 _regs[]       │
└──────────────────────────────────────────┘
```

**实现关键：**

1. **同一内存区域**：RTU 和 TCP 初始化时绑定同一个 `_regs` 指针数组，不是两份拷贝
2. **并发安全**：两个 Modbus 任务优先级相同（均为 4），FreeRTOS 时间片轮转调度，不会同时写同一寄存器。业务逻辑（MainTask @ prio 3）只在检测到变化时才写寄存器，天然避免竞争
3. **库级改造**：将 Modbus-Serial 和 Modbus-Ethernet 库中原本 `private` 的 `_regs_head` / `_regs_last` 改为 `public`，使得 RTU 初始化后可将同一个寄存器数组传递给 TCP

### 3. 输入消抖滤波（软件去抖）

> 💡 **面试高频考点：为什么不用硬件 RC 滤波？软件消抖如何实现？**

#### 硬件消抖 vs 软件消抖

| 方案 | 优点 | 缺点 |
|------|------|------|
| 硬件 RC 滤波 | 无 CPU 开销 | 需要额外元件（R+C），截止频率固定不可调 |
| 软件消抖（本方案） | 无额外 BOM 成本，消抖时间可通过 Modbus 动态配置（1~100ms） | 需要 1ms 定时任务，消耗少量 CPU |

#### 算法实现（状态计数法）

```cpp
// 核心逻辑（X_filter 任务，每 1ms 执行一次）
if (digitalRead(Temp_X0) == LOW)   // 检测到低电平
{
    if (x_buffer[0] < FilterTime)  // 计数器未达到阈值
        x_buffer[0]++;             // 递增计数
    else
        Input.X0 = 1;              // 达到阈值，确认有效信号
}
else                                // 检测到高电平
{
    x_buffer[0] = 0;               // 立即清零计数器
    Input.X0 = 0;                  // 信号失效
}
```

**设计要点：**
- **非对称处理**：下降沿需要累计 N ms 才确认（滤除抖动），上升沿立即响应（快速释放）
- **可配置阈值**：`Input_Filter_Time` 通过 Modbus 寄存器 4 动态调整，适应不同现场干扰强度
- **效率**：8 路输入共用同一个 `X_filter` 任务，每路仅消耗 1 字节计数器和若干位操作

### 4. EEPROM 参数管理策略

> 💡 **面试考点：EEPROM 写入寿命有限（约 10 万次），如何避免写穿？**

#### 设计策略

| 策略 | 实现 |
|------|------|
| **被动保存** | 只有上位机显式写寄存器 3 = 10 才触发 `Save_Parameter()`，不会自动高频保存 |
| **版本校验** | `ConfigVersion` 字段（当前=2）作为 EEPROM 数据的"Schema 版本号"。结构体新增字段时递增版本号，固件升级后自动检测不匹配并恢复出厂，避免读取到错位数据 |
| **完整性标志** | `InitFlag = 66`（魔数）。首次上电或数据损坏时自动触发 `Parameter_Init()`，确保系统始终在合法参数下运行 |
| **批量读写** | `EEPROM.put(0, myPar)` 一次性整块写入，而不是逐个字段写（减少写入次数） |

#### 数据流

```
上电启动
  │
  ├─ EEPROM.get(0, myPar)
  │    │
  │    ├─ InitFlag == 66 && ConfigVersion == 2 ?
  │    │    YES → 加载成功，使用 EEPROM 参数
  │    │    NO  → 恢复出厂默认值 → EEPROM.put() → 重启
  │    │
  │    └─ Load_ParameterTORegister()   // 参数 → Modbus 寄存器
  │
运行时
  │
  ├─ 上位机修改寄存器 24~30（硅链参数）
  ├─ 上位机写寄存器 3 = 10（保存指令）
  ├─ Save_ParameterFromRegister()  // 回读寄存器 → EEPROM
  └─ 参数持久化完成
```

### 5. 容错与鲁棒性设计

> 💡 **面试亮点：嵌入式系统必须有"防御性编程"思维。**

#### ADS1115 初始化重试机制

```cpp
uint8_t retryCount = 0;
while (!InitializeADS1115())           // 尝试初始化
{
    if (++retryCount > 5)              // 最多重试 5 次
    {
        // 降级策略：设置标志值 32767，通知上位机 ADC 故障
        setHreg(15, 32767);           // AI0=32767 表示故障
        setHreg(16, 32767);
        vTaskDelete(NULL);            // 退出 IIC 任务
    }
    vTaskDelay(1000);                 // 间隔 1s 重试（给硬件恢复时间）
}
```

**设计要点：** 不是无限重试（会阻塞看门狗），而是有限重试 + 降级运行 + 通知上位机。

#### 报警消抖（5 秒延时确认）

```cpp
// 越上限报警：信号持续 5s 才触发
if (KM > Target + DeadBandUpper)
{
    if (alarmOverTime == 0)
        alarmOverTime = millis();     // 开始计时
    else if (millis() - alarmOverTime >= 5000)
        alarmOver = true;             // 5s 后确认报警
}
else
    alarmOverTime = 0;                // 信号消失，重置计时
```

**为什么需要消抖？** 电力系统中负载投切会引起电压瞬间波动（几十到几百毫秒），如果不消抖会频繁误报警。5 秒是工业现场的常见经验值。

#### 看门狗分级保护

```
┌──────────────────────────────────────┐
│        独立看门狗 (IWatchdog)          │
│   硬件定时器，不受软件状态影响          │
│   超时 = 400ms                        │
│   喂狗频率 = 每 200ms                  │
│          (超时时间 / 2)                │
├──────────────────────────────────────┤
│  保护范围:                             │
│  - 死循环 / 任务阻塞                   │
│  - 中断风暴导致调度停止                 │
│  - 内存踩踏导致 HardFault             │
│  - Flash 等待状态异常                  │
└──────────────────────────────────────┘
```

**为什么不喂狗就会复位？** 独立看门狗使用 LSI (内部低速振荡器 ~40kHz)，与主系统时钟完全独立。即使主时钟停振，看门狗仍然会计数并复位 MCU。

#### 防止除以零

```cpp
if (myPar.StepVoltage == 0)
    myPar.StepVoltage = 500;  // 回退默认 5.00V，防止除以零死机
```

### 6. 硅链继电器编码设计

> 💡 **面试考点：3 个继电器如何实现 8 个档位？**

本质上是一个 **3 位二进制编码器**。Y2/Y3/Y4 分别对应 bit0/bit1/bit2：

| 档位 | Y2(bit0) | Y3(bit1) | Y4(bit2) | 二进制值 | 降压值 |
|------|----------|----------|----------|----------|--------|
| G0 | 0 | 0 | 0 | 000 | 35V |
| G1 | 1 | 0 | 0 | 001 | 30V |
| G2 | 0 | 1 | 0 | 010 | 25V |
| G3 | 1 | 1 | 0 | 011 | 20V |
| G4 | 0 | 0 | 1 | 100 | 15V |
| G5 | 1 | 0 | 1 | 101 | 10V |
| G6 | 0 | 1 | 1 | 110 | 5V |
| G7 | 1 | 1 | 1 | 111 | 0V |

**编码特点：**
- G7（直通/0V 降压）= 全部导通（111B），符合硅链"全短路=无降压"的物理特性
- G0（最大降压 35V）= 全部断开（000B），硅链串联所有二极管
- 编码表是**非标准二进制映射**（不是 G0=000, G1=001 就是升序），需要查表转换

**反向解码（手动模式下从继电器状态反推档位）：**

```cpp
static uint8_t RelayToGear(uint8_t y2, uint8_t y3, uint8_t y4)
{
    for (uint8_t i = 0; i < 8; i++)
        if (GearRelayTable[i][0] == y2 &&
            GearRelayTable[i][1] == y3 &&
            GearRelayTable[i][2] == y4)
            return i;
    return 0;
}
```

## 注意事项

1. **ADS1115 初始化失败**：寄存器 15~18 将显示 `32767`。检查 I2C 连接 (PB8/PB9) 和模块供电。
2. **看门狗超时**：ERROR_LED 闪烁表示发生过看门狗复位，检查是否有任务阻塞超过 400ms。
3. **EEPROM 写入寿命**：约 10 万次。参数保存操作 (寄存器 3 写 10) 会触发写入，避免高频循环改写。
4. **降压模块校准**：若降压模块实际分压比不是 91:1（R上=900kΩ/R下=10kΩ），需在代码 `Parameter_Config.h` 中修改 `HM_Calibration` / `KM_Calibration` 的默认值（×100，如 91.00→9100），或通过 Modbus 寄存器动态写入后保存。
5. **Modbus 库修改**：为实现 RTU/TCP 共享寄存器，已将 Modbus-Serial 和 Modbus-Ethernet 库中的 `_regs_head` / `_regs_last` 从 `private` 改为 `public`。若更新库版本需重新修改。
6. 本程序供学习参考。若用于商业/工业场景，请自行评估并承担风险。

### 高频面试问题速查

#### Q1: 为什么用 FreeRTOS？有什么优缺点？

**答：** 项目需要同时处理 Modbus 通信（100ms 内必须响应）、1ms 输入消抖、1s 硅链调压、看门狗喂狗四个不同时间粒度的任务。裸机超级循环需要用状态机拆分，维护成本高；FreeRTOS 让每个任务独立运行，通过优先级抢占保证实时性。

**缺点：** 每个任务需要预分配堆栈，20KB RAM 中约 5KB 被任务堆栈占用（通过 `uxTaskGetStackHighWaterMark()` 实测优化到最小）。另外 FreeRTOS 本身约 3KB Flash 开销。

#### Q2: 任务优先级为什么这样分配？

**答：** 优先级遵循"安全 → 采集 → 通信 → 业务"四层金字塔：
- 看门狗最高（6），确保系统任何情况下都能复位恢复
- 输入滤波次之（5），1ms 定时采集不能被通信任务拖延
- Modbus 通信第三（4），保证协议实时响应
- 业务逻辑最低（3），硅链 1s 调节周期允许被抢占

#### Q3: 为什么不用 PID 控制？

**答：** 硅链只有 8 个离散档位（0~7），输出不是连续的。PID 的连续输出需要量化映射到 8 档，反而会引入量化误差和频繁换档。本项目采用**基于偏差的步进式滞回控制**，每一步都是整数档位，计算简单、响应快、不会振荡。

如果未来升级为**连续可调硅链**（比如 PWM 控制 IGBT），会考虑加 PID 环路。

#### Q4: ADC 采样值如何换算为实际电压？

**答：** 
1. ADS1115 16 位 ADC，增益 ±4.096V，ADC 值 `0~32767` 对应 `0~4.096V`
2. 外部降压模块将高压（~220V DC）分压至 ADC 量程内，分压比约 91:1（R上=900kΩ / R下=10kΩ）
3. 优化：原始浮点公式改为整数运算 `(adcValue × 4096 × calibration) / 32767000`，避免 Cortex-M3 无 FPU 时触发软浮点库（节省 ~200 CPU 周期 + 2KB Flash）

#### Q5: 如何保证 Modbus RTU 和 TCP 的并发安全？

**答：** 两个 Modbus 任务优先级相同（均为 4），FreeRTOS 时间片轮转调度。更关键的是：业务逻辑任务（MainTask @ prio 3）只读取寄存器，写入操作通过 Modbus 回调函数在通信任务上下文中执行，不会出现"业务任务写到一半被通信任务读到脏数据"的情况。这是**通过优先级设计天然避免竞态**，而不是加锁（加锁在资源紧张的 MCU 上是奢侈品）。

#### Q6: EEPROM 掉电保存有什么坑？怎么解决？

**答：** 三个坑：
1. **写入寿命**（~10 万次）：只在用户显式发送"保存"指令时才写入，不是自动保存
2. **写入期间断电**（数据损坏）：`InitFlag` 魔数 + `ConfigVersion` 版本号双重校验，不匹配则恢复出厂
3. **结构体版本升级**：新增字段时递增 `ConfigVersion`，旧数据自动识别并重新初始化

#### Q7: 生产环境中 ADC 芯片初始化失败了怎么办？

**答：** 本项目的策略是**有限重试 + 降级运行**：
- 重试 5 次，间隔 1s（给硬件足够的恢复时间）
- 5 次失败后，将 AI0~AI3 寄存器设为 `32767`（全 1 标志值，通知上位机"传感器故障"）
- IIC 任务自删除，不影响其他任务继续运行（Modbus 通信、数字 IO 仍正常）
- 不会无限重试阻塞看门狗

#### Q8: 为什么继电器用开漏模式而不是推挽？

**答：** STM32F103C8 的 GPIO 在推挽模式下输出高电平为 3.3V，而大多数继电器模块需要 5V 驱动信号。开漏模式 + 外部上拉电阻到 5V 可以实现 3.3V→5V 的电平转换，同时具备"线与"能力。
